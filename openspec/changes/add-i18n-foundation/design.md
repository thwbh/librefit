## Context

LibreFit is English-only. A `rust-i18n` layer (`src-tauri/src/i18n/localize.rs`, `locales/en.yml`, `i18n!(...)` in `lib.rs`/`main.rs`) was started and abandoned — `localize_validation_errors` has **no call site**, so it is dead. The strings users actually see come from two places: inline prose in `#[validate(message = "...")]` attributes (e.g. `body.rs:22` `"Age must be between 18 and 99 years."`), and hardcoded English in ~82 Svelte components.

The app is a Tauri SPA: `adapter-static`, `ssr = false`, SPA fallback `index.html`. There is no server runtime at request time — locale must be a client-side runtime concern. Validation is generated by `tauri-typegen`: each `#[validate(message = X)]` is inlined into the generated zod schema (`src/lib/api/gen/types.ts`) as a literal `{ message: X }`, and the generated command wrappers run `safeParse` client-side before `invoke`. Rust `.validate()` runs the same rules server-side as defense.

Constraints from existing conventions: `_conv-user-errors` (ERR) owns how errors surface as toasts via the `error-formatter.ts` / command-hooks boundary; `_conv-validation` (VAL) owns validation rule shapes; `_conv-modals` governs the Settings modal UX. `_conv-test-traceability` requires every new scenario to be cited by a test.

## Goals / Non-Goals

**Goals:**

- One translation runtime (Paraglide) owning all rendered prose.
- A clean ownership rule: the backend emits **keys**, never prose; the frontend owns all text.
- A single key→message resolution point reused by both the client-zod and Rust-`Err` paths, with testable key-resolution and unknown-key-fallback behavior even under a single locale.
- A project configured so a second locale is additive (messages file + registration), not structural.
- Remove the dead `rust-i18n` stack.

**Non-Goals:**

- Any user-facing language selection, device-locale detection, or persistence (deferred to the future selection change).
- Shipping a second translation — only `messages/en.json` is populated; the app stays English.
- Extracting the ~82 components' static labels (mechanical churn, follow-up).
- Backend locale awareness or a `set_locale` command (backend stays locale-agnostic).
- Translating DB-seeded reference data beyond food-category `longvalue`.

## Decisions

### D1 — Paraglide in runtime/non-routing mode (not the SvelteKit adapter)

Paraglide's SvelteKit integration assumes URL-based locale routing (`/en/...`, `/de/...`), which is wrong for a single-window Tauri SPA. We use the compiled `$lib/paraglide/runtime` directly: `setLocale(locale, { reload: false })` plus an `overrideGetLocale` that reads persisted state. Messages author in `messages/{en,de}.json` under `project.inlang/settings.json`; the Paraglide Vite plugin compiles to `src/lib/paraglide/` (gitignored).

_Alternatives:_ `svelte-i18n` (runtime dictionaries, no compile step, no routing opinions) — simpler to wire but no compile-time key typing and weaker tooling. Paraglide chosen for typed message functions and tree-shaking; its routing adapter is simply not used.

### D2 — Backend emits keys; the `#[validate(message)]` attribute holds the key

Rewrite every `#[validate(..., message = "prose")]` to `message = "loc.<domain>.<rule>"`. Because typegen inlines this into the generated zod schema, the **key** flows to the client automatically; Rust `.validate()` yields the same key server-side. Wizard warning/classification keys (`wizard.rs`, already `message = "wizard.warning.underweight"`-style) stay as keys. No Rust translation remains.

_Alternatives:_ a structured typed error channel carrying a `TranslationKey` enum — rejected, see D3.

### D3 — CI lint for key integrity, NOT a `TranslationKey` enum / type-level enforcement

The appealing idea was a Rust `TranslationKey` unit enum → typegen `z.enum` union → an exhaustive `Record<TranslationKey, () => m.x()>` resolver, making any drift a compile error. It fails on inspection: typegen inlines `#[validate(message = X)]` as a plain zod **string literal**, not a `z.enum` member, so validation keys (the large majority of backend-emitted keys) cannot gain compile-time safety no matter what. The enum would only have protected the ~6 wizard keys, and only after retyping that field. Since a runtime/CI check is required regardless, a single uniform lint is simpler and covers everything.

`scripts/check-i18n-keys.mjs` (sibling to `check-spec-traceability.mjs`): collect keys emitted by Rust (scan `#[validate(message = "...")]` and the wizard selection sites) and assert each resolves in `messages/en.json`. Wired into `npm run lint:conventions`.

_Alternatives:_ enum + exhaustive Record (compile-time, but can't reach validation keys and needs a field retype); no check at all (silent missing-string bugs). Lint chosen for uniformity and zero new codegen.

### D4 — Single resolution boundary at `error-formatter.ts`

`formatZodError` (client-zod path) and `formatInvokeError` (Rust-`Err` path) are already the one choke point feeding toasts. Key→message resolution lives here: a backend-emitted key is looked up in Paraglide; an **unknown** key falls back to a generic localized message and is logged — it MUST NOT render the raw key to the user.

### D5 — Fixed base locale now, extension point for later (no selection UI)

The app runs on the base locale (`en`) only. The Paraglide runtime is initialized once to `en`; there is no language picker, no device-locale detection, and no persistence in this change. "Open for extension" is a configuration property, not a feature: adding a locale later requires only (a) a new `messages/<locale>.json`, (b) registering the locale in `project.inlang/settings.json`, and (c) wiring a `setLocale(...)` call to whatever future selection surface is built — none of which touches the resolution boundary (D4), the backend keys (D2), or the lint (D3). Device-locale default and a persisted `LibreUser.language` column are explicitly deferred to the future selection change, keeping this groundwork free of a migration for a preference nothing yet sets.

### D6 — Food-category `longvalue` becomes a frontend-only key

Rust never selects a category label, so it is **not** a backend-emitted key — it is seeded display data. A Diesel migration rewrites seeded `food_category.longvalue` rows to keys (e.g. `loc.food_category.lunch`); `getFoodCategoryLongvalue` resolves the key via Paraglide. This keeps the backend-emitted-key surface small and the lint scoped to Rust-selected keys only.

### D7 — Conventions authored directly, not as opsx deltas

Per project policy, `_conv-loc` (new, prefix `LOC`) and the edits to `_conv-user-errors` (ERR-004 wording) and `_conv-validation` (messages are keys) are hand-written directly under `openspec/specs/`. This change has **no** opsx-managed spec delta: nothing in a feature spec changes behavior (no selection UI; food-category labels render the same English). The groundwork's behavioral contract lives entirely in the hand-authored `_conv-loc` convention. `LOC` is added to the CLAUDE.md prefix registry.

## Risks / Trade-offs

- **Silent missing-string drift** (a backend key with no message) → `check-i18n-keys.mjs` in `lint:conventions`; D4 fallback guarantees a raw key never reaches the user even if the lint is bypassed.
- **Lint is CI-time, not compile-time** → accepted in D3; the cost of compile-time safety (enum + field retype) buys protection for only ~6 keys and still can't cover validation keys.
- **Groundwork ships an all-English app** → by design (groundwork, not finish line); the mechanism is exercised end-to-end under the single base locale, and Paraglide falls back to `baseLocale` per missing message, so a future locale's gaps render English rather than breaking.
- **`localStorage`-only persistence doesn't survive app data reset** → acceptable for a display preference; the `LibreUser.language` column remains an easy future upgrade without reworking the mechanism.
- **Deleting the `rust-i18n` stack while tests reference English prose** → migrate those assertions to keys in the same change; the dead-code deletion is safe because no live path calls `localize_validation_errors`.
- **Paraglide used against its documented SvelteKit grain** (D1) → low risk; the compiled `runtime` API is stable and public, we simply bypass the routing adapter.

## Migration Plan

1. Add Paraglide + Vite plugin + `project.inlang` + `messages/en.json`; initialize the runtime to the base locale.
2. Add key→message resolution + unknown-key fallback in `error-formatter.ts`.
3. Reword `#[validate(message)]` sites to keys; confirm regenerated `types.ts` carries keys; migrate affected tests to assert keys.
4. Diesel migration for `food_category.longvalue` → keys; update `getFoodCategoryLongvalue`.
5. Delete `src-tauri/src/i18n/`, `locales/`, `rust-i18n` dep, `i18n!` macros.
6. Add `scripts/check-i18n-keys.mjs`; wire into `lint:conventions`.
7. Hand-author `_conv-loc`; edit ERR-004 / `_conv-validation`; register `LOC`.

Rollback: the change is additive on the frontend and deletive on the dead Rust stack; reverting the commit restores prior behavior with no data migration beyond the reversible `longvalue` rewrite.
